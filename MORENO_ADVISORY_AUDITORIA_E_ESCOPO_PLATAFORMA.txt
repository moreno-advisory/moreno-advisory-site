# Moreno Advisory - Auditoria Atual e Escopo Solicitado para Plataforma Integrada

Data da consolidacao: 2026-08-06
Projeto local auditado: /run/media/cemoreno/Nexus/moreno-advisory

Objetivo deste documento:
Registrar em texto o estado atual auditado do projeto Moreno Advisory e acrescentar a nova solicitacao do proprietario: incluir tecnicamente o CRM e o APP interno no projeto, interligando tudo ao site publico, com objetivo de evoluir para um software interno completo para a Moreno Advisory, semelhante em conceito ao HubSpot.

Importante:
Este documento e apenas um briefing textual para revisao externa. Nenhum arquivo do site, CRM ou app foi alterado durante a auditoria.


# 1. Resumo Executivo

O projeto Moreno Advisory possui atualmente um site publico principal na raiz do workspace, construido com Next.js, TypeScript, React, Tailwind CSS e next-intl para versoes em ingles e portugues.

Tambem existem duas aplicacoes paralelas no mesmo workspace:

- crm/
- moreno-advisory-app/

Segundo o proprietario, o CRM e o APP tecnicamente nao estao funcionando hoje. Mesmo assim, eles devem ser considerados no escopo futuro, pois a intencao e transformar o projeto em uma plataforma integrada:

- Site publico institucional e comercial.
- App interno da Moreno Advisory.
- CRM proprio.
- Area administrativa para atualizar ou alterar conteudo do site.
- Sistema operacional interno da empresa, com funcionalidades parecidas com HubSpot.

A recomendacao tecnica e nao tratar isso apenas como "repaginacao visual do site". O escopo real e uma evolucao de produto: site publico + CRM + software interno + CMS/admin + integracoes.

# 15. Recomendacao de Arquitetura

Ha duas opcoes principais:

Opcao A - Monorepo com apps separados

- apps/web: site publico.
- apps/internal: app interno/CRM/CMS.
- packages/ui: componentes compartilhados.
- packages/db: schema e acesso ao banco.
- packages/config: configuracoes compartilhadas.

Vantagens:

- Separacao clara entre site publico e app interno.
- Melhor controle de seguranca.
- Escalavel para produto interno grande.
- Facilita deploy separado.

Desvantagens:

- Exige reorganizacao maior.
- Mais trabalho inicial.

Opcao B - Um unico Next.js app

- Site publico em rotas /en, /pt etc.
- App interno em /app, /admin ou /dashboard.
- APIs no mesmo projeto.

Vantagens:

- Mais simples no inicio.
- Menos configuracao.
- Pode reaproveitar layout, autenticacao e banco com rapidez.

Desvantagens:

- Pode ficar grande e acoplado.
- Requer muito cuidado com autenticacao, permissoes e boundaries entre publico e privado.

Recomendacao inicial:

Para um objetivo parecido com HubSpot, a melhor solucao tecnica tende a ser monorepo ou uma arquitetura modular clara. Porem, se a prioridade for velocidade e MVP, pode-se unificar primeiro em um unico Next.js app bem organizado, desde que as areas publica e privada sejam claramente separadas.

# 18. Extensao/Modulo Solicitado - Multiusuarios, Cloud Central e Sincronizacao

Nova solicitacao acrescentada pelo proprietario:

Criar uma extensao de modulo/suplemento para o sistema CRM e APP atual que implemente gerenciamento de multiplos usuarios administradores com base de dados centralizada em nuvem.

O objetivo pratico:

- O proprietario tera seu usuario principal.
- Um socio ou novo usuario tambem podera entrar.
- Esse novo usuario podera ter permissao Admin/Owner equivalente.
- O sistema devera funcionar em qualquer PC, desde que acesse o dominio/app correto.
- Os dados nao devem depender da maquina local.
- Leads, clientes, negocios, logs, tarefas e demais registros devem morar em banco cloud centralizado.
- Alteracoes feitas por um usuario devem aparecer para o outro em tempo real ou quase tempo real.


## 18.1. Observacao Sobre Google One e Google Cloud

O proprietario informou que ja paga mensalmente o Google One e deseja usar "o cloud do Google".

Ponto tecnico importante para validacao externa:

- Google One e um plano de armazenamento/servicos pessoais do Google.
- Google Cloud Platform (GCP) e a plataforma de infraestrutura para hospedar aplicacoes, bancos, APIs, Cloud Run, Cloud SQL, Firestore etc.
- O site atual ja esta preparado para Google Cloud Run.
- Para banco de dados centralizado e app multiusuario, provavelmente sera necessario usar recursos do Google Cloud Platform, nao apenas Google One.
- Google One pode ajudar com armazenamento pessoal/Drive, mas nao substitui banco de dados transacional para CRM.

Possiveis caminhos dentro do ecossistema Google:

1. Cloud Run + Cloud SQL PostgreSQL
   - Mais adequado para CRM relacional.
   - Bom para leads, contatos, empresas, negocios, permissoes e relatorios.
   - Exige configurar instancia Cloud SQL e variaveis/secrets.

2. Cloud Run + Firestore
   - Bom para sincronizacao em tempo real e dados documentais.
   - Pode ser mais simples para realtime, mas exige modelagem cuidadosa para CRM.

3. Supabase/Postgres hospedado fora do Google
   - Ja existe indicio de Supabase no projeto atual.
   - Mais simples para autenticao, banco e realtime.
   - Porem nao seria "Google Cloud puro".

4. Google Firebase
   - Inclui Auth, Firestore e realtime.
   - Pode ser uma alternativa natural se prioridade for login, realtime e multiusuario.
   - Precisa avaliar compatibilidade com o app atual e custo/controle.

Recomendacao para o GPT externo avaliar:

- Se a prioridade for usar Google Cloud: Cloud Run + Cloud SQL PostgreSQL + possivelmente Pub/Sub/WebSockets/SSE para realtime.
- Se a prioridade for velocidade de MVP: Supabase Auth + Supabase Postgres + Realtime pode ser mais rapido.
- Se a prioridade for realtime simples no ecossistema Google: Firebase Auth + Firestore.

- Criar tabela/colecao de usuarios vinculada a organizacao principal.
- Implementar login e senha com JWT para novo usuario/socio.
- Garantir que o socio possa ter o mesmo nivel de permissao Admin/Owner do primeiro usuario.

- roles

- user_roles

Roles iniciais:

- Owner
  Controle total da organizacao, usuarios, configuracoes, CRM e site.

- Admin
  Controle administrativo equivalente ou quase equivalente ao Owner, conforme decisao do proprietario.

- Manager
  Gerencia CRM, leads, tarefas e projetos, mas nao configuracoes criticas.

- Member
  Acesso operacional limitado.

- Viewer
  Apenas leitura.

Permissoes iniciais sugeridas:

- manage_users

- manage_site_content
- manage_leads

- manage_companies

- manage_tasks

Observacao:
Apesar do pedido mencionar login e senha com JWT, para seguranca pode ser melhor avaliar:

- NextAuth/Auth.js com credentials e JWT.
- Firebase Auth.
- Supabase Auth.
- Google Workspace OAuth.

Se senha propria for usada, exigir:

- hash seguro com bcrypt/argon2.
- JWT assinado por segredo em ambiente seguro.
- refresh/expiration strategy.
- cookies httpOnly quando possivel.
- protecao de rotas server-side.


## 18.3. Vinculacao de Dominio

Requisito solicitado:

- Configurar verificacao para que acesso via dominio personalizado da empresa herde configuracoes da base Cloud centralizada.
- O funcionamento nao deve depender de qual PC local esta executando o app cliente.

Interpretacao tecnica:

- O dominio da empresa, por exemplo https://morenoadvisory.com ou app.morenoadvisory.com, deve apontar para a aplicacao hospedada na nuvem.
- O app nao deve depender de banco local.
- O dominio deve identificar a organizacao/tenant principal.
- Todos os usuarios autenticados sob esse dominio acessam a mesma organizacao e mesma base central.

Possivel desenho:

- morenoadvisory.com
  Site publico.

- app.morenoadvisory.com
  App interno/CRM.

- admin.morenoadvisory.com
  Opcional: painel administrativo/CMS.

- api.morenoadvisory.com
  Opcional: API backend separada, se arquitetura exigir.

Tabela/colecao de configuracao:

- organization_domains
  - id
  - organization_id
  - domain
  - verified_at
  - status
  - verification_token

Verificacao de dominio:

- Criar token de verificacao.
- Solicitar registro DNS TXT no dominio.
- Backend verifica DNS TXT.
- Quando verificado, dominio fica vinculado a organizacao.

Para MVP de uma unica empresa:

- A verificacao de dominio pode ser simplificada, ja que a Moreno Advisory sera a unica organizacao inicial.
- Mesmo assim, convem modelar organization_id desde o inicio para nao travar expansao futura.


## 18.4. Conexao Cloud Centralizada

Requisito solicitado:

- Isolar qualquer persistencia local existente.
- Mover/apontar todas as requisicoes de leitura e escrita para banco de dados em nuvem.
- Dados afetados: clientes, negocios, logs de atividades e outros registros operacionais.

Acao necessaria:

- Auditar crm/ e moreno-advisory-app/ para descobrir se usam localStorage, arquivos locais, mock data ou armazenamento local.
- Criar camada unica de acesso a dados.
- Proibir escrita direta em localStorage para dados importantes.
- Manter localStorage apenas para preferencias nao criticas de interface, se necessario.

Entidades que devem ir para cloud:

- usuarios
- organizacoes
- permissoes
- leads
- contatos
- empresas
- oportunidades/negocios
- etapas de pipeline
- tarefas
- projetos
- notas
- logs de atividade
- mensagens de contato do site
- inscritos na newsletter
- conteudo do site
- posts de blog
- configuracoes da empresa

Regra:
Tudo que precisa ser compartilhado entre usuarios ou maquinas deve estar na cloud.


## 18.5. Sincronizacao em Tempo Real

Requisito solicitado:

- Alteracoes feitas pelo usuario no PC A devem refletir instantaneamente no PC B do socio.

Possiveis implementacoes:

1. Supabase Realtime
   - Escuta alteracoes em tabelas Postgres.
   - Bom se Supabase for adotado.

2. Firestore realtime listeners
   - Natural se Firebase/Firestore for adotado.

3. WebSockets proprios
   - Possivel com backend dedicado.
   - Em Cloud Run, requer cuidado com conexoes longas e escala.

4. Server-Sent Events
   - Mais simples que WebSockets para eventos unidirecionais.

5. Polling curto
   - Mais facil, mas menos elegante.
   - Pode servir como fallback.

Recomendacao:

- Para MVP, usar realtime nativo da plataforma escolhida.
- Se Cloud SQL/Postgres puro for usado, avaliar WebSockets/SSE ou polling.
- Para CRM, realtime deve priorizar:
  - leads
  - negocios/pipeline
  - tarefas
  - notas
  - logs de atividade

## 18.7. Como Isso Deve Funcionar na Pratica

Cenario desejado:

1. O site publico recebe um lead pelo formulario.

2. A API do site salva esse lead na base cloud centralizada.

3. O proprietario entra no app interno em app.morenoadvisory.com.

4. O socio entra no mesmo app pelo PC dele.

5. Ambos autenticam com usuarios diferentes.

6. Ambos pertencem a organizacao Moreno Advisory.

7. Ambos tem papel Admin/Owner, se assim definido.

8. Quando o proprietario altera um lead, cria uma tarefa ou move um negocio no pipeline, o socio ve a mudanca em tempo real.

9. Quando o socio edita uma informacao autorizada do site, essa alteracao fica salva na cloud e o site publico passa a consumir o novo conteudo conforme regra de publicacao.

10. Nenhum dado critico fica preso a um PC local.


## 18.8. Cuidados de Seguranca

- Nao armazenar senhas em texto puro.
- Nao expor service role key no client.
- Usar cookies httpOnly ou estrategia JWT segura.
- Implementar middleware de protecao de rotas internas.
- Validar organization_id em todas as consultas.
- Registrar logs de atividades administrativas.
- Permitir desativar usuario.
- Implementar recuperacao/troca de senha futuramente.
- Considerar 2FA para usuarios Admin/Owner.
- Separar variaveis publicas NEXT_PUBLIC das variaveis privadas.
- Garantir que edicao de conteudo do site tenha permissao especifica.

# 21. Conclusao

O projeto atual possui um site publico funcional em Next.js, com boas bases de branding, conteudo bilingue, formularios, email, WhatsApp, SEO parcial e deploy preparado para Google Cloud Run.

Porem, o CRM e o APP existentes no workspace nao devem ser tratados como prontos. Eles precisam ser auditados e possivelmente reconstruidos ou consolidados.

A nova direcao solicitada e transformar a Moreno Advisory em uma plataforma integrada: site publico + CRM + app interno + CMS/admin + banco central + multiusuarios administradores + sincronizacao em tempo real + automacoes futuras.

A repaginacao pode incluir essa visao, mas deve ser planejada por fases para evitar quebrar o site atual e para nao misturar redesign visual com construcao de um software interno completo sem arquitetura clara.
